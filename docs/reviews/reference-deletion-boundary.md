# Reference deletion regression boundary

Issue #160: main CI run [37726915712](https://github.com/taiseimiyaji/tasteprint/actions/runs/37726915712) failed a Profile notes assertion: draft `baseVersion` was 2 instead of 1, while the accepted notes, deletion, unrelated Reference/job and GET503 assertions passed. The trace shows a real PATCH commit followed by a collection GET containing version 2 before DELETE. A matching saved-input read legitimately synchronizes the draft version; the old test captured its expected bytes before that synchronization, rather than at the known-deletion boundary.

Four controlled Mock/temporary-SQLite probes on unchanged product code establish the ordering at Profile 390px and Project 1440px. Gate collection reads before fetch while the PATCH browser reply is held. If the committed read is observed before DELETE, storage advances from version 1 to 2 before deletion; if reads are released after DELETE, storage stays at version 1. In both conditions the entire draft string remains unchanged from known deletion through the late reply, GET503, GET recovery and reload. The former pre-deletion assertion fails deterministically only in the observed condition. This is a fixture boundary defect, with no product change required.

The permanent regression now covers both notes orderings in both scopes, plus the existing image and acceptance cases. It verifies the actual committed GET and expected base version, compares every submitted draft field at known deletion, then retains strict byte equality thereafter. Deleted cards remain absent, unrelated Reference/job records remain present, and there is exactly one held write. Existing screenshots remain; the two added notes cases add no pixel captures. The separate PNG nondeterminism in Issue #159 is unchanged.
