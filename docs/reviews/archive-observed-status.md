# Observed archive state and late replies

On main a943d1d, an accepted archive reply was held while an external unarchive completed and a collection GET observed that newer state. Releasing the older reply hid the active card when follow-up GETs failed, although the database remained unarchived at design r1. Existing local write tickets did not distinguish this external update.

Project responses now expose a project-local archiveVersion. A SQLite metadata table and an archived_at update trigger persist the version without changing the original four-column projects table. Old positional INSERT statements remain compatible, old SQL archive updates advance the version, and rollback undoes both state and version. Legacy rows start at version zero; Foundation snapshots, frozen Export content and their ordering remain unchanged.

Startup installs only the metadata table and trigger in one explicit transaction, after journal mode and the existing registry tables are configured. A trigger-create error or interruption before COMMIT rolls back both objects. The owner closes the failed connection and preserves the original error even if cleanup also reports an error. Tests use temporary on-disk databases and verify unchanged project rows, Foundation records and frozen ZIP Export records after failure and restart. Successful startup, restart and repeated installation retain the counter and create only one trigger.

Accepted-reply projection compares the archive versions observed in both shared caches after cancellation. It retains higher design revisions and Export sequences independently, then gives the list and Project cache the newest known archive state, including when the list has no matching project yet. A later observed state uses a neutral accepted-update notice instead of pointing the user to the old state’s tab. Existing local operation tickets remain active. Missing legacy metadata falls back to zero, but an old server response without metadata has unknown status order. This protects known observations when projecting mutation replies; it does not guarantee globally monotonic GETs or full mixed-version operation.

Returning to older code retains the additive schema. Compatibility covers ordinary old INSERT/UPDATE statements; REPLACE, delete/reinsert, ID reuse and metadata deletion are outside that contract. There is no automatic schema DROP, database restore or counter reset. A separately restored database or reset counter requires refreshing browser caches. Existing backup guidance still requires stopping the server and copying the complete data directory. No production backup framework or real user database change is included.

Four Mock/isolated-SQLite regressions cover archive and unarchive at 1440/390, a confirmed external GET, a held older reply, follow-up GET503, and resuming a cached Project while its own GET fails. Unit coverage includes equal/reversed clocks, atomic schema installation and cleanup failures, old schema/restart and frozen records, legacy writers, rollback, status observed in either cache, asynchronous cancellation, older design data/newer status, independent projects and missing metadata. Exact-head full CI and independent final review remain merge conditions. PNG Issue159 is separate and unresolved; no image tolerance, masks or capture warmup changes are included.
