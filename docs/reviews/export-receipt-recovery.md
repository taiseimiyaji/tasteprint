# Export creation receipt recovery

Issue #250 was reproduced on main `15b0aa41aa5b6536cb7ca493414613367569a1c9` with Mock AI and temporary SQLite. An image-free ZIP was committed by the server, but its POST response was replaced with 503. After a client-side project switch and immediate return, the successful empty history cache still hid the saved ZIP. The server held one record, while the UI showed zero rows and no history-retry control; no history GET followed the failed POST. A control rejected before acceptance correctly held zero records. A fixed client clock kept the cache fresh, so the recovery result cannot depend on waiting for its stale time.

The change invalidates the exact source Export history and project-list metadata when the creation receipt fails. Active queries can recover immediately; an inactive history refreshes on return. These are reads only. The original request error remains visible, and no generation request or file download is automatically repeated. Successful receipts retain the existing cache-commit and download behavior.

Seven browser regressions cover accepted and rejected requests at 1440px/390px, read-only history recovery after a second GET failure, and an accepted request whose browser connection is aborted after switching projects. They verify project separation, the latest-Export link, explicit retry reusing the same saved ZIP, frozen r2 contents, and the distinct unsaved edit surviving navigation and reload.

Local validation passed: typecheck, 223 unit tests, built smoke, and 20 affected browser cases (seven new and 13 existing). All use isolated data and no real AI. Controlled HTTP errors and a browser request abort do not establish behavior under a physical network outage. Authentication, security/publication configuration, and real user data are outside this change.
